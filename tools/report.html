DIAGNOSIS

Too many dependency calls per catalogue

The broken catalogue fetches prices one item at a time. The fixed catalogue fetches the same prices in one batch. Both use the same eight-slot pool and simulated downstream I/O. Under load, queued work raises latency and can exhaust the pool wait timeout.

Check catalogue latency against pool activity and waiting requests. Read checkout separately: an aggregate percentile can conceal a critical operation.

How to interpret this run

Warm-up requests are excluded by request start time. Requests completing after the planned window are excluded from the summary; the raw CSV retains drained completions. Percentiles use nearest rank on raw completed requests, including errors. RPS counts completed requests per measured second, not unique customers. The task mix weights browsing four to one against purchasing; this is not an HTTP request ratio.

Locust is a closed workload: slower responses reduce the offered rate. Unfinished and drained requests are absent from percentiles. User targets are not guaranteed simultaneous active requests. Use separate generators and an arrival-rate workload before making a capacity commitment.

Pool counters cover the whole run, including warm-up. Server samples arrive roughly once per second. The demo retains orders until the stand exits; memory and database growth during soak need to be interpreted with that retention policy.
